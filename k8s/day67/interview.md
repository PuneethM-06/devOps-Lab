# Interview Questions

## 1. What should be your first step when an application is reported as down?

Never restart the application immediately.

First determine the current state by running:

```bash
kubectl get pods
```

The Pod status determines the next debugging steps.

---

## 2. Why shouldn't you immediately restart a failing Pod?

Restarting a Pod may destroy valuable debugging information such as application logs or the state that helps identify the root cause. Always investigate first before making changes.

---

## 3. Explain the common Pod states.

### Running

The Pod has been scheduled and its container is running.

Running does **not** necessarily mean the application is ready to serve traffic.

---

### Pending

The Scheduler has accepted the Pod but cannot schedule it onto any Worker Node.

Common reasons include:

- Insufficient CPU
- Insufficient Memory
- Node Selector mismatch
- Taints and Tolerations

---

### Succeeded (Completed)

The Pod completed successfully.

Common for Kubernetes Jobs.

---

### Failed

The Pod terminated because of an error.

---

### Unknown

The Control Plane cannot determine the Pod's status because communication with the Worker Node has been lost.

---

## 4. Does Running always mean the application is healthy?

No.

Running only means the container has started.

A Running Pod may still fail Readiness Probes or be unable to serve user traffic.

---

## 5. What is CrashLoopBackOff?

CrashLoopBackOff means the application inside the container repeatedly crashes.

Kubelet continuously restarts the container but introduces increasing delays (BackOff) between restart attempts.

---

## 6. What are common causes of CrashLoopBackOff?

- Application exceptions
- Missing ConfigMaps
- Missing Secrets
- Database connection failures
- Invalid configuration
- OOMKilled
- Startup failures

---

## 7. How do you debug CrashLoopBackOff?

1. Check Pod status

```bash
kubectl get pods
```

2. Inspect Pod Events

```bash
kubectl describe pod <pod-name>
```

3. Inspect logs from the crashed container

```bash
kubectl logs --previous <pod-name>
```

---

## 8. What is the difference between OOMKilled and CrashLoopBackOff?

OOMKilled is the reason the container was terminated because it exceeded its memory limit.

CrashLoopBackOff is the state indicating Kubernetes is repeatedly restarting the crashed container with increasing delays.

---

## 9. What is Pending?

Pending means the Scheduler cannot find a suitable Worker Node that satisfies the Pod's scheduling requirements.

---

## 10. Why would a Pod remain Pending?

Common reasons:

- Insufficient CPU
- Insufficient Memory
- Node Selector mismatch
- Taints
- Resource constraints

---

## 11. Which Kubernetes component generates FailedScheduling events?

The Kubernetes Scheduler.

It determines whether a suitable Worker Node exists for the Pod.

---

## 12. What is ImagePullBackOff?

ImagePullBackOff occurs when Kubernetes repeatedly fails to pull a container image from a registry and waits progressively longer between retry attempts.

---

## 13. What is ErrImagePull?

ErrImagePull is the first failed attempt to pull a container image.

Repeated failures eventually lead to ImagePullBackOff.

---

## 14. Common causes of ImagePullBackOff

- Wrong image name
- Wrong image tag
- Authentication failure
- Private registry access issues
- Registry unavailable

---

## 15. Why is kubectl logs usually not useful for ImagePullBackOff?

Because the container never starts.

Since the application never runs, no application logs are generated.

---

## 16. What does kubectl logs do?

Displays logs generated by the application running inside a container.

Example:

```bash
kubectl logs <pod-name>
```

---

## 17. When should you use kubectl logs --previous?

When debugging containers that have restarted.

It displays logs from the previous container instance that crashed.

---

## 18. What does kubectl describe do?

Displays detailed information about a Kubernetes resource.

Most importantly, it shows the **Events** section, which often identifies scheduling, image pull, probe, or restart failures.

---

## 19. When should kubectl describe be your first debugging command?

Use it whenever Kubernetes itself is unable to create or start the container, such as:

- Pending
- FailedScheduling
- ImagePullBackOff
- Probe failures

---

## 20. What does kubectl exec do?

Executes commands inside a running container.

Example:

```bash
kubectl exec -it <pod-name> -- /bin/bash
```

---

## 21. Common uses of kubectl exec

- Verify environment variables
- Check mounted ConfigMaps
- Check mounted Secrets
- Test DNS resolution
- Test network connectivity
- Inspect application files

---

## 22. Can kubectl exec be used on a Pod in ImagePullBackOff?

No.

The container has never started, so there is no running process to enter.

---

## 23. Explain a production Kubernetes debugging workflow.

1. Run:

```bash
kubectl get pods
```

2. Identify the Pod status.

3. If Pending or ImagePullBackOff:

```bash
kubectl describe pod <pod-name>
```

4. If CrashLoopBackOff:

```bash
kubectl describe pod <pod-name>

kubectl logs --previous <pod-name>
```

5. If Running but unhealthy:

```bash
kubectl logs <pod-name>
```

6. If further investigation is needed:

```bash
kubectl exec -it <pod-name> -- /bin/bash
```

7. Identify the root cause.

8. Apply the fix.

9. Verify the application is healthy.

---

## 24. Which commands should every Kubernetes engineer know?

```bash
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl logs --previous <pod-name>
kubectl exec -it <pod-name> -- /bin/bash
```

---

## 25. Production Best Practices

- Never restart Pods without investigation.
- Use `kubectl get pods` to identify the Pod state first.
- Read Events using `kubectl describe`.
- Use application logs before making assumptions.
- Use `kubectl exec` only when the container is running.
- Fix the root cause instead of repeatedly restarting the Pod.
- Follow a structured debugging workflow instead of guessing.
